# FetchNow: дополнение по зависимостям frontend

Дата: 18 сентября 2026. Проверка выполнена после явного разрешения пользователя отправить имена и версии пакетов во внешний реестр npm.

**Результат: npm отметил 8 пакетов — 2 critical, 4 high, 2 moderate.** Это количество записей о затронутых пакетах, не количество независимых эксплойтов и не оценка безопасности всего сайта. Некоторые записи связаны: Astro → sharp, Vitest → @vitest/mocker.

Проверен текущий `web/package-lock.json` командой `npm audit --json --ignore-scripts --package-lock-only`. Команда завершилась кодом 1 из-за найденных уязвимостей, а не ошибки соединения. Исходный результат сохранён в [npm-audit.json](security-reviews/2026-09-18/npm-audit.json). Зависимости и lock-файл не менялись.

## Применимость к FetchNow

[Конфигурация Astro](web/astro.config.mjs:4) использует `output: "static"`. В [Dockerfile](web/Dockerfile:25) финальный этап — Nginx; туда копируется каталог `dist`, а Node, Astro и инструменты тестирования остаются на этапе сборки. Поэтому совпадение версии с advisory само по себе не подтверждает возможность атаковать production через HTTP.

В исходниках не обнаружены Astro `Image`/`Picture`/`getImage`, server islands, `define:vars` или динамические transition-директивы. Штатная команда тестов — `vitest run`; конфигурация не включает UI/API или browser mode. Действующие процессы на сервере в этом дополнении не обследовались; вывод относится к конфигурации репозитория.

## Пакеты с критической отметкой

### Astro 5.12.8 — critical по npm

Наиболее серьёзное уведомление — [GHSA-26w7-cxv4-gfx2](https://github.com/withastro/astro/security/advisories/GHSA-26w7-cxv4-gfx2): обработка специально подготовленного AVIF через стандартный Sharp image service может приводить к выполнению кода. Необходимо, чтобы атакующий смог передать изображение в обработку. Это условие не найдено в текущем frontend; API скачивания видео написан на Python и не вызывает Astro для обработки медиа.

Уязвимость всё равно важна для сборки и будущих изменений. Разработчик указывает исправление в Astro 7.2.8 с Sharp 0.35.4. В npm также перечислены другие проблемы Astro: middleware/SSR, server islands, image endpoints, dev server и генерация HTML. Их наличие не означает, что соответствующие функции используются FetchNow.

**Рекомендация:** выбрать поддерживаемую версию, закрывающую все актуальные advisories, и проверить совместимость отдельным обновлением. Не ограничиваться предлагаемым npm переходом на 5.18.2: эта версия ниже указанной в уведомлении границы исправления AVIF.

### Vitest 3.2.4 — critical по npm

[GHSA-5xrq-8626-4rwp](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp) касается доступного Vitest UI/API и отдельных сценариев Windows/browser mode. Проект использует обычный однократный запуск тестов. Наличие открытого UI на машине разработчика или сервере не проверялось.

Отдельное [GHSA-82fw-gwwq-j7x9](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9) касается redirect mocks и чтения файлов через dev-server интеграцию; upstream указывает исправление в 4.1.11. Для неаутентифицированной атаки нужны публичные mocker/interceptor plugin exports; Vitest browser mode имеет дополнительные ограничения доступа.

**Рекомендация:** обновить Vitest вместе с его внутренними пакетами до согласованной исправленной версии и не выставлять UI/API в общедоступную сеть. Предложение npm установить 3.2.7 не закрывает весь набор возвращённых advisories. Для первой уязвимости границы версий в npm и upstream отличаются; версия проекта 3.2.4 находится в уязвимом диапазоне обоих источников.

## Остальные отмеченные пакеты

- **sharp 0.33.5 — high:** транзитивная зависимость Astro, ошибки библиотек обработки изображений. Связана с описанным выше риском AVIF; отдельно не считать вторым подтверждённым способом атаки production. [Уведомление](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c).
- **fast-uri 3.1.5 — high:** ошибки разбора URI; в lock-файле приходит через `yaml-language-server → ajv`, то есть инструменты разработки. Не обнаружен как валидатор URL Python API. Версионная граница из npm для этих записей — 3.1.6. [Уведомление](https://github.com/advisories/GHSA-f65p-4m7j-42xc).
- **js-yaml 4.3.1 — high:** расход CPU на специально сформированных YAML merge-структурах. Используется зависимостями Astro/Markdown и ESLint; публичный приём пользовательского YAML в frontend не найден. Граница исправления из npm — 4.3.2. [Уведомление](https://github.com/advisories/GHSA-2883-xcg3-v3hh).
- **nanoid 3.3.17 — high:** бесконечный цикл в специальных генераторах при нулевом размере; приходит через PostCSS. Соответствующий вызов из пользовательских запросов не обнаружен. Граница из npm — 3.3.18. [Уведомление](https://github.com/advisories/GHSA-2v37-7h3g-55p8).
- **devalue 5.9.0 — moderate:** DoS при разборе некорректных данных; зависимость Astro. Публичный серверный parser devalue в статическом frontend не обнаружен. Граница из npm — 5.9.1. [Уведомление](https://github.com/advisories/GHSA-9rgm-9g3h-6x36).
- **@vitest/mocker 3.2.4 — moderate:** связан с Vitest и advisory GHSA-82fw-gwwq-j7x9 выше; обновлять совместно с Vitest.

Названия, уровни и границы в этом списке взяты из сохранённого ответа npm. Указанная граница исправляет перечисленный advisory, но не является обещанием отсутствия новых проблем в этой версии.

## Отдельно: доступ к dev server

В `web/astro.config.mjs` задано `server.host: true`. Поэтому при запуске Astro dev server он может слушать сетевые интерфейсы машины, а не только localhost. Это не настройка финального Nginx-образа. Пока зависимости не обновлены, предпочтительно ограничить dev server loopback либо явно доверенной сетью и не публиковать его туннелем. Без проверки firewall нельзя утверждать, что он сейчас доступен из интернета.

## Следующий шаг

В отдельной ветке обновить Astro/Sharp и Vitest согласованными наборами, затем оставшиеся транзитивные пакеты. Запустить typecheck, тесты, production-сборку и проверить CSP, платежные страницы и скачивание. Повторить `npm audit`; автоматический `audit fix --force` не запускался. Серверные Python-пакеты, PostgreSQL, Nginx, FFmpeg и ОС контейнеров требуют отдельной проверки.

Исходные приоритеты по защите очереди и публичной тестовой оплате сохраняются: результаты npm их не заменяют. Прямой эксплуатационный путь через найденные npm-пакеты к текущему статическому production-сайту не подтверждён.
