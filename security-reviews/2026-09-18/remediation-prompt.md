# Готовый промпт: устранение замечаний безопасности FetchNow отдельными PR

Ты работаешь над безопасностью FetchNow. Выполни программу ниже небольшими проверяемыми PR. Основная цель — сохранить работающий сайт и тестовые пользовательские сценарии, закрыть подтверждённые пробелы, затем повторно проверить безопасность.

Параметр запуска: `TARGET_PR=SEC-XX`. Если номер не указан, начинай с SEC-00. За один запуск реализуй только выбранный PR и необходимые ему проверки. Остальные PR не объединяй с ним. Если его реальная зависимость ещё не готова, сначала покажи конкретную зависимость и подготовь независимую часть работы.

## Контекст и источники

Проект: репозиторий FetchNow. Публичный сайт: `https://fetchnow.online`.

Прочитай:

- `security-reviews/2026-09-18/assessment.md`;
- `security-reviews/2026-09-18/dependencies.md`;
- `security-reviews/2026-09-18/npm-audit.json`;
- применимые AGENTS.md, документацию архитектуры и текущую конфигурацию репозитория.

Исходные замечания: FN-01 — приём заданий и очередь; FN-02 — связь тестовой оплаты с Premium; FN-03 — обход cookie-квоты; FN-04 — изоляция сетевых запросов инструментов; FN-05 — зависание Docker-вызовов деплоя; FN-06 — HSTS. Отдельно отмечены уязвимые npm-пакеты.

Отчёты являются исходными доказательствами, а не вечной истиной. Перепроверь применимость каждого замечания к текущему коду. Отдельно обозначай: подтверждено в исходниках, проверено в изолированной среде, проверено на действующем сервере, остаётся неизвестным. Не объявляй SSRF/RCE доказанным только по отсутствию сетевой изоляции или совпадению версии библиотеки с advisory.

## Обязательное решение владельца о платежах

**Тестовая оплата остаётся включённой до завершения аудита сайта.** В SEC-00—SEC-11 сохраняй создание тестового заказа, форму Robokassa, callback, выдачу тестового Premium и проверку его возможностей. Не скрывай кнопку, не выключай checkout, не вводи список тестировщиков и не отзывай выданный тестовый доступ под видом исправления другого PR.

Общие ограничения инфраструктуры защищают и тестовый Premium от перегрузки, но не должны менять его продуктовые возможности. Premium не освобождает от глобальной ёмкости системы; это отличается от бесплатной квоты.

FN-02 до SEC-12 имеет статус «временно сохранено по решению владельца», а не «исправлено». SEC-12 выполняется только после того, как владелец подтвердил завершение аудита и дал команду переходить к снятию тестовой оплаты. Самостоятельно считать любое успешное сканирование таким подтверждением нельзя.

Отключение тестовой оплаты не означает включения настоящих списаний. Боевые платежи — отдельный сценарий, которому нужны реальные настройки и отдельная проверка.

## Правила работы с проектом и сервером

1. Сначала проверь ветку, изменения и актуальную базу PR. Во время подготовки программы ветка была `feat/reliability-a-gateway-routing`, с изменёнными и неотслеживаемыми файлами. Не предполагай, что это состояние сохранилось. Не включай чужую работу в security PR и не теряй неотслеживаемые файлы. Перед переносом изменений обеспечь восстанавливаемую копию, включая необходимые untracked-файлы; обычного stash create для них недостаточно.
2. Используй отдельные ветки `codex/security-sec-XX-<slug>` либо принятый в проекте формат. Независимые PR начинай от проверенной базовой ветки; зависимые явно связывай. Если исправление зависит от незавершённого reliability PR, укажи это, а не копируй весь его diff.
3. Никаких force-push, удаления истории, массового staging, несвязанных рефакторингов, переписывания продукта или замены фреймворка ради аудита.
4. Разработка и тесты проходят локально и в изолированном окружении. На рабочем сервере в рамках проверки разрешены только необходимые операции чтения при наличии доступа. Не проводи flood, сканирование внутренних сервисов, массовое создание аккаунтов/заданий, платежи или удаление данных в production.
5. Сначала подготовь конкретный diff, тесты, порядок применения и отката. Деплой, применение миграций, изменение firewall, перезапуск сервиса и отзыв привилегий на рабочем сервере выполняются только по отдельной команде владельца. Не требуй повторного разрешения на уже явно разрешённую операцию.
6. Не выводи секреты. Для серверной диагностики извлекай только нужные поля; полный docker inspect, env и конфиги могут содержать пароли. Документы не должны содержать токены, cookies, строки подключения или пользовательские URL с секретными параметрами.
7. Не запускай одновременно повторные проверки, если предыдущий процесс не завершён. У каждого тестового запуска должны быть общий таймаут и корректная остановка дочерних процессов.
8. Не ослабляй CSP, проверку TLS, allowlist провайдеров, подписи платежей, права на файлы и авторизацию ради прохождения тестов. Не превращай статический frontend в SSR-сервис без отдельной необходимости.
9. Численные лимиты выбирай по измерениям SEC-00, с объяснением и конфигурацией. Не придумывай безопасную пропускную способность сервера. Не добавляй Redis, CAPTCHA-провайдера или другой внешний сервис без обоснованной необходимости.
10. Проверка npm с передачей имён и версий пакетов владельцем разрешена. Это не разрешение выгружать исходники, секреты или приватные образы в сторонние сервисы. Остальные зависимости и образы по возможности проверяй локально.

## SEC-00 — Зафиксировать реальное состояние сервера и исходные проверки

**Результат PR:** актуальная матрица доказательств, план проверок и перечень фактических расхождений; без изменения рабочего поведения.

Проверь локальную и запущенную ревизии, источник production Compose, внешний TLS-терминатор, цепочку прокси/CDN, опубликованные порты и наличие внешнего rate limiting. При доступе к серверу прочитай фактически применённые CPU/RAM/PID-лимиты, число worker/API-процессов, права пользователей контейнеров, объём свободного диска, размер/возраст очередей и права DB-ролей. Проверяй только относящиеся к FetchNow ресурсы.

Выясни состояние backup и документированный способ восстановления. Успешный backup не равен успешному восстановлению: пробное восстановление выполняется только в отдельную БД. Если SSH-доступа или сведений нет, точно перечисли непроверенное и необходимые реквизиты, продолжая доступную часть аудита.

Не закрывай замечание по одному наличию настройки в YAML. Не копируй секретные конфиги в отчёт. Каждому существенному новому замечанию дай доказательство и отдельный scope будущего PR; не прячь его в «прочее» и не расширяй текущий PR бесконтрольно.

**Готово, когда:** версии и источники настроек прослеживаются; неизвестное явно обозначено; выбраны измеримые бюджеты для следующих PR; зафиксирован временный статус тестовой оплаты.

## SEC-01 — Ограничить длительность проверок и корректно завершать процессы

**Закрывает:** FN-05 и риск повторения локального накопления pytest-процессов.

Основные участки: `scripts/fetchnow_release/stabilize.py`, существующие runner/helpers, Makefile, CI и связанные тесты.

Реализуй ограниченные по времени Docker-проверки с учётом оставшегося общего бюджета. При отмене и таймауте заверши собственную группу процессов: сначала корректное завершение, затем принудительное после короткого grace period; дождись освобождения ресурсов. Учти процесс, чей родитель завершился, но потомки удерживают stdout/stderr. Не посылай сигналы чужим процессам или всей сессии агента.

Добавь общий таймаут тестовых команд и jobs CI. Паузы и искусственные часы в тестах должны гарантированно продвигать сценарий. Старую гипотезу о причине зависания не выдавай за доказанный дефект без воспроизведения.

Сохрани журналирование незавершённого деплоя и предусмотренную процедуру recovery. Прерывание Docker CLI не доказывает остановку операции Docker daemon; не повторяй миграции автоматически и не маркируй неизвестный результат успешным.

**Проверки:** зависающая локальная заглушка; потомок переживает лидера; таймаут; отмена; успешная команда; ограниченный вывод; блокировка и состояние операции после отказа. Проверяй отсутствие оставшихся собственных потомков. Не используй тяжёлый CPU-цикл для тестирования таймаута.

**Готово, когда:** проверка заканчивается в заданный срок, не оставляет процессов и не повреждает модель деплоя; есть инструкция безопасного повторного запуска.

## SEC-02 — Обновить Astro и зависимости production-сборки

**Закрывает:** применимые advisories Astro/Sharp и связанные устаревшие транзитивные зависимости.

Основные файлы: `web/package.json`, `web/package-lock.json`, конфигурация Astro и Dockerfile только при необходимости совместимости.

Сверь версии с текущими официальными advisories. Не считай `npm audit fix` источником гарантированно безопасной версии: в сохранённом ответе предложены версии ниже границ некоторых исправлений. Выбери согласованный поддерживаемый набор Astro/Sharp и транзитивных пакетов. При major-переходе опиши требуемые изменения. Не применяй случайные overrides, скрывающие несовместимость.

Сохрани статическую сборку, финальный Nginx-образ, маршруты, SEO-поведение, CSP, media flow и тестовую оплату. Убери общесетевой bind dev server по умолчанию; предоставь явный opt-in для согласованного просмотра по LAN. Не меняй сетевую доступность production этим параметром.

**Проверки:** чистая установка по lock-файлу, typecheck, frontend-тесты, production-сборка, проверка маршрутов и security headers, отсутствие Node/Astro server в финальном образе. Повтори npm audit и сопоставь оставшиеся записи с условиями эксплуатации.

**Готово, когда:** перечисленные advisories устранены либо для неустранимых отдельно представлены точная причина, ограничение применимости и срок пересмотра; уязвимость не скрыта отключением проверки. Исключение риска требует решения владельца.

## SEC-03 — Обновить Vitest и добавить воспроизводимую проверку зависимостей

**Зависит от:** SEC-02.

Обнови Vitest, его mocker и связанные инструменты согласованным набором. Сохрани однократный `vitest run`; не включай UI/API/browser server и сетевой доступ без необходимости. Закрой оставшиеся advisories инструментов разработки, включая fast-uri и js-yaml, если они ещё присутствуют в их дереве.

Добавь воспроизводимые проверки npm и Python-зависимостей; для образов используй локальный сканер и фиксируй проверенный digest. Сначала установи фактический состав Python runtime и базовых образов. Не заявляй, что выполненный npm audit проверяет FFmpeg, PostgreSQL, Python или ОС.

В CI различай найденную уязвимость и недоступность источника advisories: отсутствие ответа не должно давать зелёный результат «уязвимостей нет». Не используй безусловные `|| true` или blanket-ignore. Исключения — только по конкретному advisory с причиной, областью применимости и датой пересмотра. Не отключай dev-аудит только ради нулевого счётчика.

**Проверки:** тесты работают без UI-сервера, CI имеет таймауты, отчёт пригоден для сравнения версий, сбой источника данных явно виден. Искусственные ответы сканера проверяются локальными fixtures, без публикации приватных данных.

**Готово, когда:** зависимости проверяются воспроизводимо, старые записи Vitest устранены и в production не попали инструменты тестирования.

## SEC-04 — Доверенная цепочка прокси и ограничения входящих запросов

**Закрывает часть:** FN-01/FN-03.

Основные участки: внешний Nginx в принятом проектом управлении конфигурацией, `deploy/nginx/nginx.conf`, API startup/middleware и Settings.

На основе SEC-00 определи реальный адрес клиента. Доверяй forwarded-заголовкам только от известных прокси; запрос напрямую не может выбирать свой адрес произвольным X-Forwarded-For. Внешний прокси должен формировать проверенную цепочку, а gateway — корректно её учитывать. Не своди всех пользователей к loopback-адресу внешнего Nginx.

Введи отдельные бюджеты для создания задач, validate/probe/resolve, выпуска анонимных идентичностей и служебного polling. Подключи API_CONCURRENCY_LIMIT либо замени его понятной работающей настройкой. Ограничивай до дорогостоящей работы. Различай 429 для частоты клиента и 503 для общей недоступной ёмкости; документируй Retry-After.

Polling, cancel, health и платёжные callback не должны случайно попадать под слишком жёсткий общий лимит. Callback получает отдельно обоснованный бюджет с возможностью штатных повторов; не лишай его проверки подписи. Не нарушай потоковую выдачу, Range и browser grants. Для клиентского UI добавь спокойную обработку 429/503 без бесконечного повторения.

**Проверки:** подмена forwarded-заголовков, реальная цепочка из двух прокси, IPv4/IPv6, общий NAT, разные endpoint-классы, большой поток только в локальной среде, доступность health/cancel при занятой ёмкости. Проверь, что фактический выбранный механизм конкурентности не блокирует аварийные маршруты вопреки требованиям.

**Готово, когда:** обход лимита через заголовки не проходит и обычные сценарии остаются работоспособными. Новый узкий bottleneck/API-lock не создаётся.

## SEC-05 — Атомарный контроль ёмкости очередей

**Зависит от:** SEC-04. **Закрывает основную часть:** FN-01.

Основные участки: jobs/downloads service и repository, PostgreSQL-транзакции, Settings, публичные ошибки и frontend.

Определи, какие состояния занимают ёмкость: queued, running/leased, зарезервированные операции. Ограничь общую очередь и активные задачи; для inspection и download бюджеты должны быть понятны и согласованы с числом обработчиков.

Контроль должен быть атомарным между несколькими API-процессами. Отдельные `COUNT` и `INSERT` без общей защиты неприемлемы. Сначала используй возможности существующего PostgreSQL; новый сервис допускается только при обосновании. Не удерживай DB-lock во время DNS, HTTP или работы медиапроцессов. Если нужны предварительные reservations, обеспечь TTL и освобождение после сбоя.

Повтор идемпотентного запроса возвращает прежнюю задачу, не расходуя ещё один слот. При отказе не остаются задания, резервы квоты и побочные записи. Завершение, отмена, expiry и crash recovery корректно освобождают бюджет. Premium также подчиняется общей ёмкости инфраструктуры.

Добавь безопасные метрики глубины и возраста очереди, занятых слотов и отказов. Не используй URL, токены и job ID как неограниченные metric labels; не публикуй внутренние метрики без контроля доступа.

**Проверки:** параллельные транзакции на настоящем тестовом PostgreSQL, несколько API-инстансов, новый токен на тот же URL, идемпотентный повтор, rollback, падение владельца reservation, release после cancel/expiry. Mock-only тестов для гонок недостаточно.

**Готово, когда:** ни один конкурентный сценарий не превышает заданный предел и система восстанавливает ёмкость после сбоя.

## SEC-06 — Ограничить злоупотребление анонимными идентичностями

**Зависит от:** SEC-04/SEC-05. **Закрывает часть:** FN-03.

Сохрани текущие Secure/HttpOnly/SameSite cookies, случайные серверные токены и базовый анонимный сценарий. Добавь бюджет выпуска новых идентичностей и инфраструктурные бюджеты операций, которые нельзя обнулить простым удалением cookie. Используй доверенное определение клиента из SEC-04.

Не называй IP уникальным человеком и не обещай полный запрет обхода анонимной квоты: VPN и распределённые клиенты остаются возможны. Раздели бесплатную продуктовую квоту и защиту от злоупотреблений. Не внедряй скрытый fingerprinting; для хранения сетевых идентификаторов определи минимизацию и срок хранения, а для хеша — защиту от простого перебора, если это применимо.

Если измерения показывают необходимость CAPTCHA или подтверждаемого аккаунта, подготовь отдельное решение; не добавляй провайдера и регистрацию без согласования продукта. Поведение при недоступном общем хранилище лимитов должно быть явным: не выдавать бесконечный новый бюджет из-за сбоя.

**Проверки:** многократные запросы без cookie, неизвестный/просроченный cookie, конкурентный bootstrap, разные пользователи за одним NAT, подмена IP, переход Free→тестовый Premium, сбой хранилища. Платёжный тестовый сценарий продолжает работать.

**Готово, когда:** новые cookie не обходят общий бюджет ресурсов, а остаточные ограничения анонимной модели честно описаны.

## SEC-07 — Ограниченная очистка заданий и контроль хранения

**Зависит от:** SEC-05/SEC-06.

Разбери lifecycle metadata jobs, download jobs, artifacts, browser grants, quota reservations, anonymous clients и платежных ссылок. Согласуй политику retention с существующими FK и recovery. Не удаляй финансовые записи и историю прав по TTL временного файла; не отзывай тестовый Premium в этом PR.

Реализуй очистку ограниченными пакетами с безопасным параллельным запуском, лимитом времени и понятным прогрессом. Не загружай все просроченные строки в память и не держи одну огромную транзакцию. Активное задание, действующая аренда или поток выдачи не должны терять необходимый объект. Добавь индексы только под реальные запросы.

Перепроверь `TEMP_STORAGE_MAX_BYTES`: настройка должна реально ограничивать суммарный объём либо быть заменена честно описанным механизмом. Сохрани уже существующие проверки min-free и размера файлов; учти, что RAM-лимит контейнера не ограничивает named volume и журналы Docker. Документируй безопасные пороги и ротацию журналов в управляемой конфигурации.

**Проверки:** повторная очистка, два cleanup-процесса, прерывание между пакетами, FK на платежи/права, активная выдача, backlog просроченных задач, временно недоступный storage. Данные тестов только искусственные.

**Готово, когда:** таблицы и временные файлы имеют контролируемое хранение, очистка ограничена по ресурсам и не разрушает работающие сценарии.

## SEC-08 — Отделить выполнение медиапрограмм от управляющего worker

**Подготавливает:** FN-04; само по себе замечание ещё не закрывает.

Основные участки: worker orchestration, process runners, yt-dlp/FFmpeg/FFprobe adapters, контейнеры и протокол результата.

Опиши и реализуй минимальную границу: управляющий worker имеет необходимые права БД, а обработчик недоверенного медиа получает только конкретную задачу и ограниченный доступ к её рабочей области. Недостаточно очистить env дочернего процесса, если тот остаётся под тем же UID и может читать окружение/файлы управляющего процесса.

Используй минимальный подход, совместимый с инфраструктурой проекта. Не монтируй Docker socket в приложение и не выдавай privileged для запуска песочницы. Не превращай изолированный executor в публичный endpoint произвольного выполнения команд. Протокол содержит серверно выбранные операции и ограниченные данные, а не shell-строку или клиентские флаги.

Сохрани fixed argv, ограничения stdout/stderr, таймауты, отмену всей группы процессов, канонизацию URL, lease/fencing и проверку результата. Ограничь CPU/RAM/PID, права, capabilities и mounts. Подбери seccomp/no-new-privileges без отключения нужной защиты ради совместимости.

**Проверки:** инструмент не читает секреты/файлы управляющего процесса и соседней задачи; размер результата ограничен; поддельное сообщение отвергается; потеря executor и отмена корректно завершают задание; все поддерживаемые media-сценарии работают на fixtures.

**Готово, когда:** граница процессов/прав существует и проверена. В отчёте FN-04 пометь «изоляция подготовлена, egress ещё не проверен» до SEC-09.

## SEC-09 — Ограничить исходящие соединения песочницы

**Зависит от:** SEC-08. **Закрывает оставшуюся часть:** FN-04.

Применяй сетевую политику именно к изолированному медиапроцессу. Он не должен обращаться к PostgreSQL, управляющему worker, Docker daemon, loopback/private/link-local/cloud metadata. Управляющий процесс сохраняет только необходимый ему доступ к БД.

Выбери контролируемый egress proxy либо подходящий механизм сетевых namespaces/firewall; обоснуй его. Проверь IPv4 и IPv6, DNS, редиректы и повторное разрешение имён. HTTP-проверка перед запуском yt-dlp не заменяет контроль фактического соединения. При CONNECT/туннелировании защищай действительное назначение, а не только первоначальное имя.

Разрешённые CDN и провайдеры должны работать без снятия TLS verification и без «временного allow all». Если для протокола нужен HTTPS-only или ограничение портов, проверь реальные сценарии и зафиксируй это в контракте. При отказе слоя контроля инструмент не должен незаметно уходить напрямую в интернет.

**Проверки:** в отдельной тестовой сети используй фиктивные внутренние сервисы, редиректы public→private, смену DNS-ответа, IPv6/mapped-формы, отказ прокси. Докажи отсутствие достижения запрещённого тестового сервиса, а не только наличие ошибки на верхнем уровне. Проверка не должна обращаться к настоящему metadata endpoint или рабочей БД.

**Готово, когда:** обходы блокируются на уровне соединения, скачивания провайдеров проходят и подготовлен точный план применения/отката без изменения production в этом PR.

## SEC-10 — HSTS на реальном TLS-терминаторе

**Зависит от:** SEC-00. **Закрывает:** FN-06.

Изменяй управляемую конфигурацию внешнего HTTPS-сервера, а не только внутренний HTTP-gateway. Если она не хранится в проекте, подготовь версионированный шаблон и порядок применения, согласованный с текущей схемой эксплуатации.

Добавь HSTS на HTTPS-ответы, включая ошибки. Выбери поэтапный max-age: сначала короткий для проверки, затем целевой после подтверждения стабильности TLS. Не включай includeSubDomains/preload без проверки всех поддоменов. Сохрани HTTP→HTTPS redirect, обновление сертификатов и CSP для Robokassa.

**Проверки:** конфигурационный тест Nginx, HTTPS 200/4xx/5xx в тестовом окружении, отсутствие конфликтующих заголовков, redirect, тестовые платёжные страницы. Учти кэш HSTS: откат файла конфигурации не отменяет уже сохранённую браузером политику мгновенно.

**Готово, когда:** изменение проверено в тестовой среде и готово к отдельному применению на сервере; факт production-заголовка подтверждается только после реального применения.

## SEC-11 — Повторный аудит и проверка собранной системы

**Зависит от:** SEC-01—SEC-10. **Тестовая оплата остаётся включённой.**

Собери актуальные версии в изолированном окружении. Проверь весь путь: URL → inspection → очередь → download → авторизованная выдача/Range → отмена/expiry → cleanup; отдельно Free и тестовый Premium.

Используй двух тестовых клиентов: чужой job/download/grant нельзя прочитать, отменить или повысить в правах. Проверь неподписанный, изменённый и повторный callback на тестовой среде; браузерный return не меняет заказ. Проверь повторные запросы при сетевом сбое и недоступности БД/исполнителя.

Выполни ограниченную по времени и объёму проверку нагрузки на staging: входные бюджеты, очередь, память, процессы, временный диск, доступность health/cancel и восстановление после перегрузки. Это не нагрузочный тест production. Проверь восстановление синтетической резервной копии в отдельную БД.

Повтори сверку зависимостей и образов; сопоставь реально проверенный образ с будущим release digest. Для каждого FN укажи реализацию, тестовое доказательство, состояние применения на сервере и остаточный риск. В частности, FN-02 остаётся отложенным по решению владельца.

**Готово, когда:** есть итоговый отчёт без пустых утверждений «всё безопасно», перечислены все непроверенные области, регрессии устранены и владелец может принять решение о завершении аудита. Успешный SEC-11 автоматически не запускает SEC-12.

## SEC-12 — Снять тестовую оплату после завершения аудита

**ОТЛОЖЕН: только после подтверждения владельца. Закрывает FN-02.**

Убери публичную возможность создавать тестовые заказы на production на стороне сервера и в UI. Предотврати выдачу новых обычных production-привилегий из тестового источника. Разделение test/live должно быть серверным и прослеживаться по данным, а не только по кнопке или клиентскому флагу.

Подготовь инвентаризацию ранее выданных тестовых прав без персональных данных. Предложи точный способ истечения/отзыва по происхождению, отдельно от настоящих прав. Не удаляй платежные записи и не отзывай права до согласованного применения. Определи поведение для повторных и запоздалых тестовых callback: они не должны восстанавливать production-привилегии.

Сохрани тестовый сценарий в отдельной тестовой среде. Если live-платежи ещё не готовы, production checkout остаётся выключенным; не включай реальные списания автоматически. Проверь readiness, документацию и конфигурационные guards против случайного возврата публичного тестового режима.

**Проверки:** публичный API не создаёт тестовый заказ; клиентский флаг не обходит запрет; тестовый источник не активирует production Premium; старый callback не восстанавливает права; настоящие права не затронуты; staging-тесты работают.

**Готово, когда:** согласованное переключение выполнено и проверено отдельно; в отчёте FN-02 закрыт доказательством, а не только изменением кода.

## Единый формат завершения каждого PR

Перед завершением выполни необходимые проверки, соразмерные изменению. Не подменяй их тестами, которые только повторяют реализацию. Не запускай повторно весь набор без причины после уже успешной проверки.

Предоставь:

1. Номер и заголовок PR; какую проблему и сценарий он исправляет.
2. Короткое описание поведения до/после и список затронутых границ.
3. Результаты тестов: команда/сценарий, фактический итог, непроверенные условия.
4. Изменения настроек, миграций, совместимости и ресурсов; порядок применения и отката.
5. Статус каждого соответствующего FN: исправлено в коде / проверено в staging / применено на сервере / остаётся неизвестным.
6. Подтверждение, что тестовая оплата сохранена для SEC-00—SEC-11.
7. Только реальные оставшиеся блокеры и следующий зависимый PR.

Не называй PR созданным без ссылки на него. Не называй замечание исправленным на сервере, если выполнены только локальные изменения. Не заявляй отсутствие уязвимостей по одному зелёному сканеру.
